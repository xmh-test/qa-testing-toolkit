# bug提交

适用于不同模块，不内置特定项目、平台、设备或人员配置。

使用 Meegle 飞书项目 CLI 工具（[项目地址](https://github.com/larksuite/meegle-cli)），安装与认证问题单独处理。

## 内容原则

让他人看得懂，并能在自己的环境复现。只写用户提供、实际观察或可信测试记录支持的事实，不补造条件、预期规则、原因或复现频率；未验证问题不能写成已确认缺陷。

- 保留必要的本地操作及与客户端的交互，不限定步骤发生在客户端内。
- 将个人文件名、路径、设备地址等偶然信息泛化，保留影响复现的类型、大小、数量、权限及特殊名称／路径特征。例如“从本地电脑拖拽一个 MP4 视频文件到客户端上传”。
- 正文写可执行的操作和可观察的结果，不叙述 Figma／原型依据或测试者内部工作过程；必要的数据准备写成通用步骤，排查细节放备注。凭证不写入缺陷。
- 信息缺失、歧义、冲突，或不确定某条件是否影响复现时，先集中询问用户，不擅自补写、删除或泛化；确认前不提交受影响条目。跟踪平台不等于实际复现平台。

## 默认指派与版本信息

- **默认指派**：新建或重新打开 Bug 时，用户没有明确指定经办人／负责人，就优先指派给当前飞书项目工具授权用户本人。通过当前登录身份查询取得该用户，并按目标项目的真实人员、角色及经办人字段元数据解析 ID；不把本机用户、聊天发起者、历史提交人或机器人身份当作授权人。已知默认值无需再次询问；无法确定授权用户、该用户不可指派或存在多个经办角色无法确定时，说明并集中询问，不自行换人。用户明确指定的个人或项目分配规则优先。仅追加证据／评论时保留原经办人，除非用户明确要求重新指派。
- **被测程序版本**：新建 Bug 的描述必须写明本次实际复现的平台、被测客户端／程序名称及版本号；多个端分别列出。优先使用当前程序版本页、构建信息或本轮可信测试记录；不能把系统版本、测试工具版本、历史 Bug 版本或默认最新版本当作当前被测版本。构建号、渠道等已知且影响区分版本时一并保留；无法取得必要版本信息时先询问，不猜测后提交。
- **补充也带版本**：重开说明、补充描述和证据评论都注明本次被测程序的平台、名称及版本，即使原描述已有版本也不省略。区分历史版本与本次复现版本，不覆盖原有历史信息；项目版本字段不能代替描述／评论中的版本说明。

## 六项结构

| 字段 | 内容 |
| --- | --- |
| Bug 标题 | `[功能模块] 触发条件与具体故障现象`，避免“功能异常”等空泛表述 |
| 前置条件 | 本次实际复现的平台、被测程序名称与版本，以及必需的环境、状态、权限和测试数据条件 |
| 操作步骤 | 按顺序描述操作，页面和按钮使用实际名称 |
| 预期结果 | 应出现的行为或结果，可包含本地文件结果 |
| 实际结果 | 观察到的现象、提示原文或文件结果，附与问题匹配的真实证据 |
| 备注 | 必要日志、接口报错、复现频率等排查信息；无内容可留空 |

## 证据与呈现

- 必须有能支持该条实际结果的真实证据。界面问题优先使用截图；接口、后台任务、性能等问题可使用请求响应、日志、测量记录或视频，不把截图作为所有缺陷的提交前提。
- 截图可来自客户端、本地目录或其他相关现场，必要时多图对比并说明各图现象。不制作模拟界面或伪证据；标注不改变事实，画面完整、清晰可读。
- 证据优先通过富文本呈现：新建描述中，支持内嵌的截图、GIF／视频放在“实际结果”相关文字之后；已有 Bug 的新增证据优先放入补充评论，紧随本次实际结果说明；简短的请求响应、日志或测量记录用文本、代码块或表格呈现，排查细节放备注。按当前 Meegle 工具的富文本及图片上传规范使用真实返回的引用，不手工拼接上传地址或资源标识。
- 富文本不支持该格式、超过当前工具／平台限制，或内容过大影响阅读（如大量日志）时，改用附件；所在描述或评论保留证据摘要、文件名及对应现象，必要时摘录关键片段。不能因改用附件而省略关键证据，也不把上传成功等同于正文可见。
- 缺少截图但已有足够的其他证据时可继续提交；证据不足时，在授权范围内补齐，无法取得则说明并集中询问用户，不提交受影响条目。不为补证据扩大设备、数据或操作权限。

## 查重与已有 Bug 处理

- **提交前检索**：在已确认的目标项目及缺陷类型中，结合模块、触发条件和故障关键词检索，不只做标题精确匹配，也不只查未关闭项。按需换用同义关键词、读取相关分页，取得候选的描述、平台、版本、状态及解决／关闭原因。查询失败、权限不足或结果截断时说明查重限制，不把未查到当作不存在；无法完成必要查重时暂停该项创建。
- **判断是否同一问题**：对照触发条件、实际现象、预期、平台与版本及已有处理记录，不凭同名、同一用例或相似报错直接合并，也不因标题不同或平台／版本不同直接另建。不要求先证明根因相同。明确属于同一问题则复用已有 Bug ID；疑似重复、多个候选无法确定归属，或历史关闭原因与本次判断冲突时，展示候选链接、相同点和差异，集中询问用户后再决定。
- **批内去重**：同时对照本批待提交项、已确认复用项和已成功创建项。同一问题合并证据与平台结果，只处理一个 Bug；同一用例发现的不同故障分别记录。维护本批条目与目标 Bug ID／链接的对应关系，恢复任务时先读执行记录，不重复创建。
- **按当前状态处理**：每次写入前重新读取已有 Bug 的状态和内容。未解决／处理中等活跃状态保持原状态，补充本次新增信息，不另建单；已解决或已关闭且确认同一问题在本次版本仍存在／再次出现时，重新打开该 Bug 并补充信息。状态依据项目真实元数据和状态含义判断，不凭状态 ID、顺序或完成态名称猜测；拒绝、重复、取消等其他终态须结合处理原因判断，不一律当作可重开。
- **补充内容**：追加本次复现的平台与版本、必要前置条件、步骤差异、实际结果、真实证据及“仍存在／再次出现”的事实；注明原处理状态与重开原因，不编造修复版本、时间、根因或频率。保留原描述、历史证据和讨论；重开说明及新增证据优先提交到评论区，用富文本评论承载，不在原描述中追加。每条补充评论包含本次被测程序的平台、名称与版本；评论不可用或无权限时报告待补充，不自动改写原描述，只有用户明确要求时才改用描述补充。相同补充已存在时不重复追加，更新环境等字段时合并保留历史信息，不把本次未复现端标为复现。
- **重新打开的流程**：核对本次被测程序版本和默认／明确指定的经办人，读取当前状态允许的流转、目标状态及所需字段，通过项目支持的状态流转／回滚操作进入实际的重开或待处理状态，不直接改写状态字段或猜测流转 ID。提交任务已授权处理同一问题的补充与重开时不重复确认；只整理草稿或用户排除更新／重开时，不执行这些操作。无可用路径、权限或必填信息时停止该项并说明，不靠新建同义 Bug 绕过。
- **回读与部分成功**：分别回读评论中的补充信息与被测程序版本、证据关联、目标状态及本次需设置的经办人。记录新增、复用补充、重新打开、无需变更、疑似重复待确认或失败等实际结果。补充成功但重开失败，或重开成功但补充失败时，保留已有成功结果，报告未完成部分，仅修复缺失操作，不再次创建 Bug，也不声称整项完成。

## 创建超时与重试

- 写入前在本批执行记录中保留目标项目、条目摘要、请求内容、尝试结果及返回的 Bug ID；工具支持幂等键时为同一创建请求复用同一键，不在重试时更换。
- 创建超时、断连或响应不明时，有 ID 先按 ID 回读；没有 ID 则结合本次请求内容、创建人和实际提交时间范围检索，并核对候选详情。确认已创建则复用该 ID，继续未完成的证据补充和校验。
- 一次查询为空不能证明创建失败；考虑检索延迟并进行有限次数的复查。仍无法确认结果时将该项标为“创建结果待确认”并停止自动创建重试，保留断点交由用户处理。只有确认未创建或服务端幂等机制能保证不重复时，才重试原创建请求。
- 更新、追加信息和重开请求结果不明时，同样先回读当前内容、评论及状态，已生效操作不重复发送。明确失败时针对原因修正，最多自动重试两次；重复失败停止该项。

## 执行与校验

1. 检查登录状态及当前授权用户身份，读取当前项目、字段与角色定义；按需查询选项、关联项和人员，用真实元数据解析 ID，不猜测或硬编码。
2. 按查重规则确认问题依据及处理方式（新增、复用补充或重开），核实本次被测程序版本并按默认指派规则确定经办人；只有确需新建时，按当前模板一次性收集缺失的批次配置（如优先级、严重程度、模块、环境、版本、关联项、人员和其他必填字段），可选项可留空，列明单条例外。沿用用户明确且仍适用的规则，不把历史条目自动当默认值。向用户展示名称。
3. 已有 Bug 的重开说明与新增证据优先写评论；仅用户明确要求优化原描述时才编辑描述。编辑前先读原文、证据及可用的记录版本标识，只更新本次授权的内容，保留其他字段；无需重新收集整套新建配置。每次写入前（包括修正和重试）重新读取待更新字段，与初读版本比较；若有他人或自动化新增内容，基于最新版本合并并保留非本次修改的内容与证据，无法无歧义合并时停止该项并询问用户。有版本号／条件更新接口时使用其防止覆盖；版本冲突后重新读取，不用旧内容强行重试。
4. 写入前展示整理结果、本次被测程序版本、经办人名称、证据情况、查重结论及拟处理的已有 Bug ID、状态与操作，说明内容写入描述还是评论；已有明确授权且信息齐全时执行，不重复确认。缺失信息按内容原则先询问。
5. 批量串行写入；每条回读标题、本次写入的描述或评论、被测程序版本、需设置的经办人及其他目标字段和证据，按上述证据呈现规则检查富文本显示及附件关联，必要时打开页面确认可见。字段被自动化覆盖或证据异常时修正并回读；无法修复则报告并询问，不标记完成。
6. 部分失败时保留成功项，按创建超时与重试规则核实后仅修复未完成部分；结果不明不盲目重放。修正后仍不一致或重复失败时停止该项。空成功响应不代表完成。
7. 最终列出标题、ID／链接、查重结论、实际处理方式、重开前后状态（如适用）、本次被测程序版本、经办人、补充评论 ID／链接（如有）、校验结果及未解决事项。
