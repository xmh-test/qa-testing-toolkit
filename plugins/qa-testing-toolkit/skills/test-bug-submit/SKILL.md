# bug提交

使用 Meegle 飞书项目 CLI 工具（[项目地址](https://github.com/larksuite/meegle-cli)），安装与认证问题单独处理。

## 内容与字段

- 只写输入、实际观察或可信测试记录支持的事实。预期须有明确需求、有效设计或已确认规则支持；依据不清先确认，纯体验诉求列为优化建议。
- 保留复现必需的操作、条件及名称／路径特征，泛化无关个人文件名、路径和地址。正文描述操作与结果，排查信息放备注；凭证不写入缺陷。
- **影响范围必填**：明确受影响的功能、流程、用户／角色或数据范围；不能以空值或“未知”代替，也不从单端现象推断全量影响。
- **运行平台由输入确认**，不从当前电脑或跟踪项目推断。部署环境暂不收集；项目“环境”字段按真实含义映射，平台不能写入部署环境字段。
- **复现频率仅按输入填写**，未提供则不写次数、频率或占位，不要求额外测试来补齐。
- **被测版本必填**：新建描述和每次补充评论均注明本次被测程序的平台、名称与版本；按当前版本页、构建信息或可信测试记录核实，多端分别列出。发现版本、复现版本、历史修复版本、计划修复版本分别记录，不互相替代或推断。
- 模块、分类和需求／用例／迭代关联，在可信资料唯一匹配时自动填写；有歧义再确认。字段和人员 ID 从项目元数据解析，不按枚举顺序猜测。
- 必填信息缺失或存在影响判断的冲突时，集中询问并暂停受影响项；其他未提供的可选信息省略。项目必填要求与本技能规则冲突时先说明并确认，不编造默认值。

## 指派

新建或重开时，用户未明确指定经办人或分配规则，就指派给当前飞书项目工具授权用户本人。查询当前登录身份并映射项目经办字段／角色；无法确定身份、角色或可指派性时询问，不用本机用户或机器人代替。仅补充评论时保留原经办人。

## 严重程度与优先级

严重程度表示影响大小，优先级表示处理紧迫程度，分别判定。取值顺序：用户明确指定、项目已确认规则、下表默认定义；映射项目实际名称及 ID。

| 严重程度 | 默认定义 |
| --- | --- |
| 致命 | 数据丢失或损坏、系统整体不可用、核心业务完全中断，且无可行绕过方式 |
| 严重 | 核心功能失败、频繁崩溃、关键结果错误，或主要流程被阻塞 |
| 一般 | 局部功能或交互异常，有可行绕过方式，主要业务仍可完成 |
| 轻微 | 不影响功能和数据正确性的视觉、文案、排版等问题 |

| 优先级 | 默认定义 |
| --- | --- |
| 紧急 | 已造成持续重大影响，或阻塞当前发布、关键验证，需要立即处理 |
| 高 | 影响当前交付目标、核心场景或较多用户，应优先安排 |
| 中 | 需要修复，但不阻塞当前关键目标，按正常计划处理 |
| 低 | 影响较小，可结合后续计划处理 |

新建时给出等级及事实依据，结合影响范围、交付阶段和已知业务时限判断；UI 或低频问题不自动归低级，未知信息不按最坏情况补全，不承诺修复日期。无法可靠判级时询问决定等级所需的信息。

补充或重开默认保留原等级；新证据表明影响变化时，展示原等级、建议等级及理由，用户确认后调整。

## 描述结构

| 字段 | 内容 |
| --- | --- |
| Bug 标题 | `[功能模块] 触发条件与具体故障现象` |
| 前置条件 | 平台、程序版本及必要状态、权限和测试数据 |
| 操作步骤 | 使用实际页面和按钮名称，按顺序描述动作 |
| 预期结果 | 有依据的应有行为或结果 |
| 实际结果 | 观察到的现象、提示原文或产物，明确影响范围并关联证据 |
| 备注 | 必要日志、接口报错及输入提供的其他排查信息 |

## 证据

使用能支持实际结果的真实截图、请求响应、日志、测量记录或视频。可基于原图标注，不改变现场，不制作模拟证据。证据不足时在授权范围内补齐，无法取得则报告并询问。

优先富文本呈现：新建描述的证据放在实际结果之后；已有 Bug 的新增信息与证据放评论。简短日志用代码块或表格；格式不支持、超过平台限制或内容过大时用附件，所在描述／评论保留摘要、文件名及对应现象。按当前工具规范上传并使用真实返回的引用。

## 查重与已有 Bug

1. 在目标项目及缺陷类型中，按模块、触发条件和故障关键词检索，包含已解决／已关闭项；按需用同义词及分页补查，读取候选详情和处理原因。无法完成必要查重时暂停该项创建，不把失败或截断的查询当作无重复。
2. 对照触发条件、现象、预期、平台、版本及处理记录判断是否同一问题，不仅比较标题，也不要求先证明根因。同一问题复用 ID；疑似重复、多候选或关闭原因冲突时展示链接及差异，询问后处理。
3. 对照本批待提交、复用及已创建项去重，记录条目到 Bug ID／链接的映射。同一问题合并证据，不同故障不因来自同一用例而强行合并。
4. 写入前回读当前状态：活跃项保持状态；已解决／已关闭且本次确认仍存在或再次出现时重开。拒绝、重复、取消等终态结合处理原因判断，不一律重开。通过项目允许的流转／回滚路径及真实 ID 操作；无路径、权限或必填信息时停止该项，不新建同义单绕过。
5. 补充评论写本次版本、影响范围、必要复现条件、步骤差异、实际结果和新证据；重开时注明原状态及重开原因。先检查已有评论，避免重复追加。保留原描述和历史；评论不可用时报告待补充，仅在用户明确要求时改写描述。
6. 编辑原描述或其他字段前重新读取并合并同期变更，仅修改授权内容；可用时采用版本号／条件更新，冲突后重新读取。用户只要求草稿或排除更新／重开时，不执行相应外部操作。

## 写入、重试与校验

- 写前展示整理结果、等级理由、经办人、查重结论及拟新增／评论／重开／编辑的目标。已有授权且必要信息齐全时执行，不重复确认。
- 批量串行处理，记录请求内容、尝试结果及返回 ID；支持幂等键时，同一创建请求复用同一键。
- 创建结果不明时，有 ID 则回读，无 ID 则按请求内容、创建人和实际提交时间范围检索候选。考虑检索延迟做有限复查；仍不明则标“创建结果待确认”并停止自动重建。只有确认未创建或服务端幂等保证不重复时才重试。
- 更新、评论和重开结果不明时先回读，已生效部分不重发。明确失败针对原因修正，最多自动重试两次；仍失败则停止该项。
- 每项回读本次内容、版本、目标字段、状态、经办人及富文本／附件可见性。部分成功时仅修复未完成操作，保留成功结果；未完成校验不标记完成。
- 最终列出标题、ID／链接、查重结论、处理方式、重开前后状态、本次版本、经办人、评论 ID／链接、校验结果及遗留事项。
