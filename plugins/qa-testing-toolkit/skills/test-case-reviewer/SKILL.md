# 测试用例评审

评审用户指定的用例及相关需求。明确模块、版本和范围；多个候选无法定位时询问，不跨项目选最新文件。仅评审不代表授权改写用例。

读取同插件 `../test-case-generator/references/common_case_rules.md` 作为唯一用例规范；JSON 评审同时读取其 `test_case_schema_v3.md`。本技能与生成器随插件一起分发。

覆盖与实际结果评审同时使用 `../test-case-generator/references/risk-design.md`；按 `../test-case-generator/references/extensions/index.md` 独立核对上下文选择并仅读匹配扩展，不能只检查已有用例的表达与字段或接受生成器的自选范围。

## 两层评审

1. JSON 运行本技能的 `scripts/validate_test_artifacts.py <JSON>`；附带默认模板总结时追加 `--summary <总结.md>`。报告原样记录结果；失败仍继续可读取部分的语义评审。用户自定义总结结构时人工检查并说明，不能按默认模板判缺陷。其他格式逐项检查对应字段，不冒充脚本已通过。
2. 对照真实需求和用例检查：
   - 范围内验收标准是否有用例或明确缺口；编号能否定位来源。缺少来源时覆盖结论为“无法确认”。
   - 含设计稿时，按同插件 `../test-ui-designer/references/source-reading.md` 检查全材料平台/页面总览和纳入/排除依据，再逐纳入项反查FP、用例/候选或具体无独立目标说明；不能只读当前节点或旧依据的平台。无目录权限标记全貌未验证，不能认定无其他平台；明确用户限定范围不作为遗漏。范围内整个平台或核心页面遗漏按严重缺陷，其他重要页面缺覆盖按重要缺陷；没有映射的静态/重复页先核对理由，不强造用例。
   - 多平台共通用例是否有各端入口、操作与判据依据并要求分别执行；PC窗口/工具/计数等没有直接套到手机。只增平台标签不等于覆盖；唯一用例数与分平台执行范围分别统计。
   - 前置数据可建立、操作明确、预期可观察、独立执行与清理可行。
   - 变更数据/资源或中断连接的用例带destructive标签，明确隔离、基线和恢复；故障构造需获执行授权，设计交付不冒充授权。
   - 核心功能是否有操作至结果的行为覆盖，是否把目标动作或成功结果放入前置条件而只检查提示。纯展示用例不替代功能行为。
   - 核心状态变更是否核对本次动作对应的对象/资源、必要业务与数据结果；已有running、按钮恢复和成功Toast不能独自证明安装、保存或重启生效。观测待准备不等于可以省略判据。
   - 从原始功能目标反查两类异常、部分结果、恢复及后续操作，而不是从当前用例数量推导完整。逐FP缺用例/候选/具体不适用说明时指出覆盖缺口；按实际能力检查外部依赖路径、作用域/设备切换、版本及平台，不扩大未知架构。
   - 核对操作前/中/后的重复、离开、连续下一操作，资源不存在/已存在/部分残留/外部变化，及失败阶段/路径是否有实质不同代表；一条笼统失败或一条全链路用例不证明所有样本已覆盖。聚合目标可以，吞掉不同触发机制不可以。
   - 核对上下文及所选扩展到FP/用例/候选的处置，既查遗漏扩展，也查滥用扩展。未选的明显适用项应解释；未知能力标待确认，明确范围外有依据。仅管理员不排除会话失效；通用多用户文档也不能自动新增普通用户权限规则。扩展是设计方法，不是新的产品需求或执行授权。
   - 规则未知与执行准备未完成是否分开；有判据的待准备用例不应被删除，候选不计作确定用例或已覆盖。无环境不自动表示设计失败，有环境也不证明判据正确。
   - 一条用例一个独立验证目标；不按页面数判定过粗，不按按钮数要求拆分。
   - 分类宽泛且一致，场景摘要有区分度，正文表达操作和结果。
   - 测试数据与业务规则分开；没有来源的边界、错误码、文案及等待阈值不当作事实。
   - 高风险异常未被机械降级，适用分支无遗漏，无重复膨胀。
   - 总结数量、优先级和追溯与 JSON 一致。
   - 来源为 UI 测试依据时，核对节点/文件定位及证据状态；部分明确项未扩展到未知部分，待确认项没有确定预期。原型表现未冒充产品规则或实测结论，界面展示与功能行为依据清楚。
   - 按关键断言核对来源，不以整条用例的来源类别替代证据。缺少连线不是否定全部行为设计的理由；说明及前后状态稿支持的功能意图应被利用。
   - Figma追溯默认使用节点链接、读取时间和范围清单；未保存本地截图本身不是缺陷，视觉读取与文件留存分别核对。需要留存截图先取得用户确认，不以评审为由主动下载或补存设计资料。
   - 用户确认是否记录实际答案、范围与新旧规则关系，候选处置及旧编号可追溯；实现观察/开发答复未静默覆盖验收决定。已确认规则应转为对应覆盖，不停留在缺口列表。

结构校验不能证明覆盖完整、分类合理或业务结果正确，不得以其替代语义评审。

## 严重程度

- 严重：核心/高风险需求遗漏、不可执行、JSON 无法解析、步骤预期错位、关键追溯错误。
- 重要：预期模糊、编造规则、遗漏重要分支、优先级失真、重复膨胀、标题结构或分类不合规范。
- 建议：不影响执行的措辞、长度和排版改善。

每项给出具体 case ID/标题、证据和修复动作，避免泛泛评价。

## 交付与完成

- 用户单独要求评审：按 `references/review_checklist.md` 保存 `评审报告_${TIMESTAMP}.md` 到用例同目录或指定目录。
- 生成器内部自检：将检查结果和残留问题写入生成总结，不默认另出文件。
- 用户要求修复时才修改已有用例；生成器自检发现自己生成的缺陷可在原任务范围内修复。
- 有严重或重要缺陷时为“不通过”；只有建议项时可为“通过（附建议）”。缺少来源、无法检查的范围标记“未验证”，不能判全面通过。
- 结论分别说明设计质量和执行准备。已明确标注的环境/样本待准备本身不是设计缺陷；伪称已就绪、遗漏核心行为或混入未经确认判据才是相应评审问题。
