# 测试计划定制

## 目标

生成可评审、可执行且不过度重复的测试计划。保留必要的功能描述和用例编写指导，明确测试范围、策略、环境、排期、人员、上线标准和风险。

测试计划描述“测什么、为什么重点测、如何组织测试以及何时允许上线”，不要代替需求分析或详细测试用例。

## 工作流程

### 1. 收集输入

从用户输入、需求文档、设计稿及同目录已有材料中提取以下信息。缺失项标记 `【待补充】`，不要编造日期、人员、版本、支持矩阵或业务规则。

| 字段 | 说明 |
|------|------|
| 项目名称 | 产品或项目名称 |
| 需求名称 | 本次需求或模块名称 |
| 需求类型 | 新功能、客户端重构、纯视觉重构、后端变更等 |
| 业务基线 | 需求文档、设计稿、上一稳定版本、已有用例 |
| 测试负责人 | 测试执行与报告负责人 |
| 预计提测时间 | 缺失时标记待补充 |
| 预计上线时间 | 缺失时标记待补充 |
| 测试端范围 | PC、Web、iOS、Android、设备型号等 |
| 影响范围 | 被直接或间接影响的模块 |

若需求属于客户端重构，明确记录：

- 已明确修改的页面和交互以需求或设计为准。
- 未明确修改的业务以重构前正式版本为基线。
- 后端未声明变更时，不自行推断后端新增逻辑，只做接口兼容与必要回归。

读取指定文档时先确认文件或链接真实存在。计划中引用本地文件时使用可解析路径或同目录相对链接，不写不存在的路径。

### 2. 判断规模与详细度

| 规模 | 判断参考 | 建议内容 | 建议长度 |
|------|----------|----------|----------|
| 小需求 | 单一功能，约 1～2 天 | 范围、策略、排期、上线标准 | 60～100 行 |
| 中需求 | 多个流程或端侧，约 3～7 天 | 完整结构 + 重点项 + 用例指导 | 140～220 行 |
| 大版本 | 多模块、高风险、1 周以上 | 完整结构 + 风险 + 回滚 | 200～300 行 |

用户未说明时按中需求生成。行数仅用于控制冗余，不得通过删除必要测试边界机械压缩文档。

### 3. 组织测试范围

测试范围必须保留“功能名称 + 一句话测试边界”，不要只列模块名，也不要展开成详细测试步骤。

推荐格式：

```markdown
- [ ] 功能名称 — 验证入口、核心规则、主要状态、异常处理和最终业务结果。
```

遵循以下规则：

- 中型计划通常列出 8～20 项本次需测功能。
- 每项说明做什么、验证到什么边界，避免“功能正常”“数据正确”等空泛表述。
- 将关联模块放入“回归范围”，不要在本次测试中重复展开。
- 将明确不覆盖的内容及原因放入“不测范围”。
- 对未确认功能使用“待确认/按原基线验证”，不要把推测写成确定需求。

### 4. 提炼重点测试项

中型和大型计划保留 5～8 个跨功能的重点测试项。重点项用于回答“为什么这里风险最高”，不能重复罗列全部测试范围。

优先考虑：

- 新旧版本业务等价性。
- 核心业务闭环。
- 异步状态和并发请求一致性。
- PC、移动端或设备差异。
- 权限、会话和敏感信息安全。
- 删除、迁移、重置等破坏性场景。
- 数据完整性、网络恢复或系统可恢复性。

### 5. 生成测试用例编写指导

中型和大型计划默认包含简洁的“测试用例编写指导”，帮助测试人员补充用例，但不要重新生成整套用例规划。

至少包含：

1. **用例基线**：说明复用哪些现有用例、哪些变更需要补充。
2. **设计方法**：说明功能点、BDD、DDT、对比用例的适用场景。
3. **编写规范**：说明标题、前置条件、步骤、预期、优先级和破坏性标记要求。
4. **优先补充方向**：列出平台专项、异常恢复、安全或需求缺口确认后的用例。

推荐方法表：

| 方法 | 适用内容 |
|------|----------|
| 功能点用例 | 页面入口、按钮、字段、跳转和正常操作 |
| BDD 场景 | 状态流转、异步恢复、跨页面或跨服务闭环 |
| DDT 数据驱动 | 输入格式、长度、边界值、枚举和组合数据 |
| 对比用例 | 重构前后未明确修改功能的业务等价性 |

不要默认估算每个模块的测试用例数量。只有用户明确要求或已有用例基线时，才记录总量和优先级分布。

### 6. 制定策略、环境和排期

- 测试策略说明“如何测”，不要再次描述“测哪些功能”。
- 同一负责人不要在策略表每一行重复写 `【待补充】`；在基本信息或人员分工表中统一记录。
- 环境只列影响执行的版本、平台、账号、设备、网络、数据、服务和日志能力。
- 有提测和上线日期时倒排实际日期；没有日期或人数时只定义阶段顺序，不虚构日历日期、固定工期或人员产能。
- 用例量较大、跨平台或包含破坏性场景时，提示必须根据执行人数和设备占用重新估算。

### 7. 设置上线标准

将“准出条件”和“上线标准”合并，避免两套重复标准。

默认标准：

- P0、P1 用例执行率和通过率均为 100%。
- 无 P0/P1 遗留缺陷。
- P2 遗留缺陷完成影响评估并取得发布确认。
- 核心业务闭环和支持矩阵通过。
- 高风险操作完成数据、账号或环境恢复。
- 输出测试报告、遗留风险和明确发布建议。

不要同时写“P1 通过率不低于 95%”和“无 P1 遗留缺陷”；如项目采用其他门槛，明确说明未通过、阻塞、跳过和延期的处理规则。

### 8. 记录风险、缺口与回滚

- 合并“风险”和“待确认项”，每项写明影响和处理要求。
- 风险描述不重复测试范围，只记录不确定性、资源限制、环境依赖和高影响后果。
- 大版本或包含破坏性操作时补充回滚方案；小需求可省略。
- 回滚方案说明触发条件、回退对象、数据保护、回滚后冒烟范围和责任人。

## 去重规则

生成或更新完成后逐项检查：

- “测试范围”只回答测什么以及覆盖边界。
- “重点测试项”只回答最高风险和跨功能关注点。
- “测试策略”只回答使用什么方式执行。
- “风险与待确认项”只回答什么尚未确定、会造成什么影响、如何处理。
- 不在“重点测试项”重新复制测试范围。
- 不在“用例编写指导”重新罗列所有功能。
- 不同时保留“准入/准出条件”和另一套“上线标准”。
- 不默认生成逐模块用例数量估算。
- 不因追求简洁而删除功能测试边界和用例编写指导。

## 质量检查

输出前验证：

- 文件名符合 `测试计划-{项目名称}-{需求名称}.md`。
- 基本信息和引用来源真实、可解析；缺失项明确标记。
- 测试范围具体且没有推测性新增业务。
- 重点项为 5～8 个且没有逐项复述范围。
- 中型/大型计划包含用例编写指导。
- 排期与已知日期、人数、设备资源相匹配；未知时不伪造。
- 上线标准无逻辑冲突。
- 风险、待确认项和回滚与需求规模相符。
- Markdown 标题层级、表格、列表和链接格式正确。
- 文档长度与需求规模匹配，无大段重复描述。
