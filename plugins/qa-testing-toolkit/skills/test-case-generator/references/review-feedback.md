# 评审反馈处理

仅在用户要求处理评审反馈或明确接入此流程时读取。普通用例生成遵循默认本地流程。反馈已导出为本地文件时直接核对该文件；涉及分支读取或其他 Git 操作时另读 [Git 与项目接入](git-integration.md)，按用户授权范围操作。

## 定位与核对

- 从项目配置确认用例仓库、输入分支、反馈分支及实际用例 JSON 映射。输入 `cases.json` 对应反馈分支同目录 `review.json`；自定义 JSON 对应同目录 `<用例文件主名>.review.json`，如 `测试用例_20261113_150000.json` 对应 `测试用例_20261113_150000.review.json`。
- 核对反馈 `project` 与 `metadata.program`、`module`、`cases_path`、本地平台和系统模块映射，确认每个 `case_id` 属于目标输入。反馈中未提供平台时依据已确认映射核对，不能从相似模块名推断。
- 对照 `candidate_commit_sha` 与要修改的输入版本，逐条检查评论的 `target_commit_sha`、字段、引用原文及 `anchor_outdated`。反馈版本滞后、用例已改变或目标不一致时先列出差异，确认适用性后处理。可用本地基线或已确认的版本证明核对，未知版本标为待确认。

## 状态与意见

当前反馈包含 `workflow_mode=case-review`、`case_counts`、`case_reviews` 和 `comments`（含回复及解决状态）等信息。

| 用例结论 | 含义 |
| --- | --- |
| approved | 通过 |
| rejected | 不通过 |
| pending | 待评审 |

`case_reviews` 保存当前逐例结论，完整操作历史由系统数据库保存。`case_counts` 用于核对当前统计。用例结论撤销后恢复 pending，评论和问题状态应独立检查；撤销结论不等于删除评论或解决问题。按评论原文、回复、解决状态和锚点版本判断待处理项。

## 修改与交付

1. 将适用意见映射到目标 `case_id`、字段或模块依据，区分可直接落实、已满足、有争议及待确认项。过期或跨模块反馈保留核对结论，不据此覆盖当前产物。
2. 修改已确认输入 JSON 及受影响的关联总结/依据，保持模块身份、有效 ID、创建时间与追溯信息。新增 ID 追加，删除 ID 不复用。反馈本身有冲突或业务规则未知时继续已明确部分。
3. 运行现有数据、适用总结与按需关联文件检查，再进行语义自检。保存意见到修改项及验证结果的对应关系，可写入已有总结的迭代摘要或最终交付说明。
4. 系统反馈由系统维护。Agent 只更新输入产物，评审通过、评论解决及反馈分支写入由系统流程决定；反馈分支保持独立，不合并进输入分支。
5. 分别报告读取的反馈版本、实际修改目标、处理/待确认意见及验证结果。只有确实执行并成功的 Git 提交或推送才列对应结果。系统“已写入反馈分支”仅说明快照已导出，Agent 已读取或已处理需要各自的实际证据。
