# 通用测试用例规范

## 标题与分类

格式：`【功能分类】【场景摘要】核心操作，预期结果`。

- 功能分类是稳定、适度宽泛的业务区域。同一区域复用名称，不以按钮、字段、单次操作、校验项或异常分支细分。
- 场景摘要只写最有区分度的条件、环境或状态。
- 不将功能名称或“信息展示”“操作检查”等检查任务充当场景条件；正文使用实际动作，不统一套用“查看对应区域”。同一业务区域不按正常/异常、操作阶段或观察渠道反复拆分类。
- 两段使用中文 `【】`；不使用 `/` 拼接层级或罗列候选项。
- 正文写操作及可观察结果，以中文逗号分隔。避免“测试正常”“验证正确”等泛称；不禁止有业务含义的词，如“确认付款”。
- 20～60 字是可读性建议，不以凑字数或删关键条件满足长度。

正例：

```text
【新建与编辑】【已填写配置】点击取消，返回列表且不创建任务
【新建与编辑】【未选择备份源】提交创建，保留配置并提示选择备份源
【新建与编辑】【有效源和目标】提交创建，新增一条任务并进入列表
```

不合格：`【新建与编辑/取消】【已填写配置】测试正常`。
示例说明表达方式，其业务结果仅在需求支持时使用。

## 粒度、数据与独立性

- 一条用例验证一个独立目标或结果分支，可跨页面、包含必要准备和操作。不同独立目标或实质不同失败路径分开。
- 前置条件说明必要角色、初始状态、环境及可获得的数据，不机械补齐无关类别。
- 功能行为用例需包含所验证的核心动作及其可观察结果；不能将目标动作或最终成功放入前置后仅查看提示。纯展示目标允许从相应状态开始，但不替代行为覆盖。
- 不依赖其他用例执行。数据变更有隔离或清理方式，可写在前置条件或步骤中。
- 数据可以构造，如创建指定名称的文件；不得将构造数据误写成产品限制、固定生产账号或真实存在的资源。
- 产品边界、错误码、提示文案、等待阈值只有来源确认时才作为强断言。未知规则列入缺口，只交付有可确定预期的部分。
- 区分规则缺口与准备缺口：判据明确而环境未就绪时保留用例，列出具体准备事项及受阻条件；判据依赖未知策略时保留为候选，不进入确定用例 JSON。UI来源候选写入UI测试依据，其他来源候选写入总结的需求缺口节，不伪装成已确认覆盖。
- 通用执行约定在依据或总结中集中说明。单例保留必要条件和具体准备项，不给无关场景重复附加长篇异步、隔离或免责声明。
- 异步步骤写观察渠道、完成信号及超时处理。有 SLA 时引用；没有时标记“执行超时阈值待确认”，不虚构“3 秒内”等验收标准，不作性能通过判断。
- 禁止无解释的 `xxx`、`任意值`、`{邮箱}`。运行期对象可写“本用例新建任务的 ID”，并说明获取方式。

## 步骤与预期

- `precondition`、`steps`、`expected` 都用 `1. 内容` 换行编号，从 1 连续递增，每行非空。
- 每步一个主要动作，给出目标元素和必要数据。可包含同一验证目标的必要后续动作。
- 预期与步骤编号、数量一一对应。输入、导航步骤写直接可见反馈，不提前写最终结果。
- 结果可从 UI、已知 API 或业务状态观察；不要求验证无法观测的内部实现。
- 选择与验证目标匹配的观察层次。提示成功不自动证明数据持久化、资源变化或业务可用；必要时设计独立结果核验，但不强制引入未确认的底层系统或新平台。

## 覆盖与优先级

- 以已知验收标准为基线，覆盖适用的成功/失败、权限、状态、边界、依赖缺失及平台差异。
- 等价类、边界值及有意义的条件组合仍用于设计普通用例，不展开无意义笛卡尔积。
- 仅对有依据且适用的平台、安全、性能维度扩展，不自动套用所有端侧检查清单。
- P0：失败会阻断核心业务或造成严重安全、数据损失的场景，包括高风险异常。
- P1：重要需求、主要分支、常见异常及关键参数规则。
- P2：低影响、低频健壮性和体验场景。不能仅因是边界或异常就归 P2。
- 按失败影响和频率定级，在总结中解释重要风险，不强制配额。

## 目录与平台

- `directory` 为 `项目名|平台分类|模块名`，`functional_module` 与第三段一致。
- `tags` 至少含一个 `web`、`mobile`、`desktop`、`api`，可在末尾追加 `destructive`；不得重复。
- 单平台目录映射：web → web、mobile → app、desktop → pc、api → api；多平台为 all。
- `functional_module` 是本批次业务模块；标题分类可以更细，但保持宽泛且稳定。
- 多平台步骤和预期一致时可合并，实质不同时拆分。
- `case_type` 使用功能用例、移动端用例、兼容性用例、性能用例、安全用例、接口用例；复合类型用 `|` 连接。
