# Git 与 Agent Case Manager 接入

用户要求 Git 操作或将用例接入内容仓库时读取。本地生成/更新默认只维护文件；git add、commit、push 分别按用户明确要求执行，交付说明记录实际范围与结果。

## 仓库、分支与模块

- 应用代码仓库与用例内容仓库独立。先核实目标路径、远端和当前分支，用例仓库可以包含多个项目和模块。
- 从项目配置读取输入分支和反馈分支。当前 Agent Case Manager 的默认值为 `cases` 和 `review-feedback`，配置值优先，输入与反馈分支应不同。
- 系统按 JSON 的 V3 内容及 metadata 发现用例，文件名和目录自由，兼容原 `cases.json`/`summary.md`。同仓库的 `program + module + platform` 对应一个持续维护模块；更新保留已确认身份和文件映射。
- 已有多个批次或候选 JSON 时核对系统映射，目标不明确时让用户选择。保持历史文件与映射，不根据文件时间戳切换目标。需要移动或改名时同步确认系统中的用例 JSON 路径，避免意外生成新模块。

## 关联文件与总结模式

1. 确定当前模块实际 JSON、需求、总结路径。新建使用稳定文件名，更新沿用已确认文件；`metadata.artifacts.summary` 指向实际总结或为 null。
2. 关联路径按 [V3 协议](test_case_schema_v3.md) 解析。优先使用相对 JSON 所在目录的明确引用，使用可选 `scripts/check_case_links.py <JSON> --root <用例仓库根目录>` 核对本地关联。summary 和 source 指定的仓库内文件必须在同一输入提交中可读，避免只有本地文件或被忽略文件。
3. 外部 URL、绝对本机路径和文字需求只保留来源说明。要在系统中捕获其内容，先按用户授权把所需文本保存到用例仓库并更新引用，然后核对实际输入提交。未完成时报告“来源信息已保留，内容未捕获”。
4. 总结默认遵循现有模板并运行数据/总结校验。用户要求自定义结构时，交付中说明人工核对范围，接入时选择“自定义总结（人工核对）”。仅 JSON 时选择对应模式；核对已有模块模式后再处理，保留用户已确认的设置。

## 获授权的 Git 操作

- 先核对工作区现有差异，只处理本次明确范围。提交前检查 JSON、实际关联文件及其在目标提交中的解析结果，说明纳入和遗漏原因；避免将其他模块或应用代码混入。
- 用户只要求本地更新时交付文件。用户明确要求 add、commit 或 push 时，按所要求的步骤继续并记录结果；提交成功才列 SHA，推送成功才声明已推送。
- 推送拒绝、分支变化或结果未知时先核查实际状态，保留已成功结果。涉及冲突或他人改动时按事实处理，不用强推覆盖。
- 读取系统评审意见时另读 [评审反馈处理](review-feedback.md)，按该流程核对目标版本及意见。系统反馈写入成功与 Agent 读取、处理分别报告。
