# 测试用例生成与更新

交付可独立执行、结果可观察、可追溯的测试用例。一条用例围绕一个独立验证目标，允许包含完成该目标所需的连续操作，不按按钮或页面数量机械拆分。

用户本次明确指定的范围、文件格式和路径优先于以下默认值。局部修改保持任务范围，不重新生成整套资产。不自动附加需求分析、测试计划或 Excel。

## 输入与模式

- 新建：使用 PRD、需求分析或明确需求描述。缺少全部需求来源时说明缺什么；局部规则未知时继续已确定部分，将受影响项列为缺口。
- 仅有 Figma/HTML 设计稿：先使用同插件 `test-ui-designer` 提取 UI 测试依据，再生成用例；已有依据时直接读取，不循环调用。从明确功能意图及可判定部分生成行为或展示用例，推导候选单列于依据，不混入确定用例。设计依据可替代 PRD，不冒充已批准业务需求。
- 更新：读取目标文件和本次变更依据。保留未涉及用例、有效 ID、来源和创建时间；新增 ID 追加，删除编号不复用。明确的用户修订本身可作为依据，不强制查找另一份需求分析。
- 多个候选输入无法按用户所指模块/批次区分时询问，不用跨项目“最新文件”代替。
- 旧格式规则见 `references/test_case_schema_v3.md`。版本升级另存 V3，默认保留旧文件；不静默丢弃无法迁移的数据。

## 所需规则

生成或修改用例内容时读取：

- `references/common_case_rules.md`：标题、粒度、数据、步骤和优先级的唯一规范来源。
- `references/test_case_schema_v3.md`：数据协议及兼容边界。
- `references/functional_point_profile.md`：覆盖与追溯。
- `references/risk-design.md`：逐功能风险展开、核心变更的独立结果核验及适用能力选择。不能只从已生成用例倒推覆盖完成。

需要确认产品策略或处理多来源冲突时，读取 `references/confirmation-and-evidence.md`。合并同类决策、给出待选方案、每批最多10个独立问题；确认记录与用例同步，明确部分继续处理。

需要总结时读取 `references/test_case_template.md`，默认保留其二级章节顺序和表头，不自行改名、合并或省略；无内容填写“无”或 N/A。用户明确指定其他结构时以用户要求为准。修复时无需重复加载已读取且没有变化的规则。

## 默认交付

同批产物使用一次取得的当前本地时间 `YYYYMMDD_HHMMSS`：

1. `测试用例_${TIMESTAMP}.json`：V3 明细，唯一用例数据源。
2. `{模块}_测试用例总结_${TIMESTAMP}.md`：统计、追溯、覆盖、自检及缺口，不复制完整步骤和预期。

输出根目录依次采用用户指定目录、输入所在 `4-test_cases`/`test_cases` 根目录、工作区已有 `4-test_cases`、最后回退 `test_cases`。新建批次置于 `{根目录}/{项目}/{模块}/{TIMESTAMP}/`；更新沿用目标目录。未知项目或模块从输入确定，不能伪造。

用户指定其他展示格式时沿用同一质量标准，不强制额外交付 JSON。局部更新仅同步确实受影响的现有总结。

## 设计与完成条件

1. 确定范围、来源、验收标准、功能点及宽泛分类。已有编号沿用；从 PRD 新建 REQ/AC/FP 时，在总结中记录编号与原文位置、规则的映射。
2. 围绕验收标准及功能目标展开成功、两类异常、恢复、权限、状态及边界；风险矩阵记录用例/候选/具体不适用原因。已有功能的通用质量目标可直接形成有依据的异常检查，不把所有未画出的失败都当未知需求。核心状态变更核验实际对象、必要业务结果及数据影响，未知专有策略再确认。测试数据可构造；业务限制和判定阈值必须有依据。
3. 生成初稿后运行本技能的 `scripts/test_case_contract.py <JSON> --summary <总结.md>`。只交付 JSON 或用户自定义总结结构时省略该参数，另行说明未按默认模板检查。该命令只证明结构与统计合规。
4. 依同插件 `test-case-reviewer` 的标准完成语义自检。自检记录在总结中，不默认另出评审报告；不等待另一次用户请求才修复本轮生成的缺陷。
5. 修复结构错误及严重/重要语义缺陷，再复查受影响内容。连续三轮仍无法解决时保留草稿并说明具体阻塞项，不得宣称通过。
6. 每条用例有具体动作和可判定预期，统计与总结一致，范围内每个验收标准有覆盖或明确缺口。准备未就绪的用例标明具体所需条件，不宣称可立即执行；未知判据保留候选。分别报告设计完整性与执行准备状态，结构检查通过不等于业务覆盖通过。

替换已有文件前校验候选文件，通过后再替换；失败保留原文件。最终回复列出文件、数量、检查结果和未解决缺口。中间文件放临时目录，不混入交付目录。
