# 测试用例生成与更新

交付可独立执行、结果可观察、可追溯的测试用例。一条用例围绕一个独立验证目标，允许包含完成该目标所需的连续操作，不按按钮或页面数量机械拆分。

用户本次明确指定的范围、文件格式和路径优先于以下默认值。默认在本地生成或更新文件。局部修改保持任务范围，不重新生成整套资产。不自动附加需求分析、测试计划或 Excel。

## 输入与模式

- 新建：使用 PRD、需求分析或明确需求描述。缺少全部需求来源时说明缺什么；局部规则未知时继续已确定部分，将受影响项列为缺口。
- 仅有 Figma/HTML 设计稿：先由同插件 `test-ui-designer` 提取测试依据；已有依据核对范围与版本后复用，缺少平台／页面总览时补齐。确定规则生成用例，未知规则保留候选。
- 更新：读取目标文件和本次变更依据。保持 metadata.program、module、platform 的已确认身份，保留未涉及用例、有效 ID、来源和创建时间；新增 ID 追加，删除编号不复用。明确的用户修订本身可作为依据，不强制查找另一份需求分析。
- 多个候选输入无法按用户所指模块/批次区分时询问，不用跨项目“最新文件”代替。
- 旧格式规则见 `references/test_case_schema_v3.md`。版本升级另存 V3，默认保留旧文件；不静默丢弃无法迁移的数据。

## 所需规则

生成或修改用例内容时读取：

- `references/common_case_rules.md`：标题、粒度、数据、步骤和优先级的唯一规范来源。
- `references/test_case_schema_v3.md`：数据协议及兼容边界。
- `references/functional_point_profile.md`：覆盖与追溯。
- `references/risk-design.md`：逐功能风险展开、核心变更的独立结果核验及适用能力选择。不能只从已生成用例倒推覆盖完成。
- `references/extensions/index.md`：场景扩展入口。先识别产品、平台、架构及能力，仅读取匹配的扩展文档；NAS、移动、Web、桌面、C/S、多用户和部署依赖可按事实组合，不将项目规则写进通用流程。

需要确认产品策略或处理多来源冲突时，读取 `references/confirmation-and-evidence.md`。合并同类决策、给出待选方案、每批最多10个独立问题；确认记录与用例同步，明确部分继续处理。

默认总结使用 `references/test_case_template.md`，保留其二级章节顺序和表头以供结构校验。用户自定义结构时按其要求交付，说明未应用默认模板检查。

## 默认交付

同一模块默认维护一套当前产物，优先沿用已确认的原 JSON 和关联总结。新建时建议使用稳定文件名：

1. `测试用例.json`：V3 明细，唯一用例数据源。
2. `{模块}_测试用例总结.md`：统计、追溯、覆盖、自检及缺口，不复制完整步骤和预期。仅 JSON 时 `metadata.artifacts.summary` 为 null。

输出根目录依次采用用户指定目录、输入所在 `4-test_cases`/`test_cases` 根目录、工作区已有 `4-test_cases`、最后回退 `test_cases`。新模块默认置于 `{根目录}/{项目}/{模块}/`；平台身份不同的模块按已确认路径分别维护。更新沿用已确认文件及目录。已有多个批次或候选文件、目标不明确时先确认映射；保留旧文件，不依赖时间戳或“最新”自动覆盖。

用户明确要求另存、归档或分批时采用其命名与目录要求。项目、模块从真实输入确定；创建时间写入 metadata，更新保留 `generated_at` 并按需记录 `updated_at`。总结引用填写实际文件，推荐相对 JSON 所在目录，如 `./文件备份_测试用例总结.md`。旧 `cases.json`/`summary.md` 和已确认的时间戳文件可继续维护。

用户指定其他展示格式时沿用同一质量标准，不强制额外交付 JSON。局部更新仅同步确实受影响的现有总结。

## 按需流程

- 仅在用户要求 Git 操作或接入用例内容仓库时，读取 [Git 与项目接入](references/git-integration.md)。普通本地生成沿用默认交付流程。
- 仅在用户要求处理评审反馈或明确接入反馈流程时，读取 [评审反馈处理](references/review-feedback.md)。反馈读取与 Git 操作分别按实际任务启用。

## 设计与完成条件

1. 确定范围、来源、验收标准及功能点。含设计稿时按 `../test-ui-designer/references/source-reading.md` 核对平台／页面总览及读取状态；局部更新复用仍有效的范围和编号。
2. 按所需规则设计用例，使用 `risk-design.md` 及适用扩展逐 FP 检查条件、故障机制、独立结果、恢复与数据保护。判据与追溯要求见 `functional_point_profile.md`；分别记录确定用例、规则候选及执行准备缺口。
3. 运行 `scripts/test_case_contract.py <JSON> --summary <总结.md>`。仅交付 JSON 或使用自定义总结结构时省略 `--summary`；该命令只证明数据结构及适用统计合规。需要核实 metadata 关联文件或做项目接入时，按 `test_case_schema_v3.md` 运行可选的 `scripts/check_case_links.py`，核对实际引用、缺失、越界和歧义。
4. 按同插件 `test-case-reviewer` 做语义自检，结果写入总结；从原始来源、总览和适用扩展反查遗漏，不用现有用例数量代替覆盖判断。
5. 修复结构错误及严重／重要语义缺陷，再复查受影响内容；连续三轮未解决时保留草稿并说明阻塞项。
6. 交付前核对动作与预期可判定、数量与统计一致、每个范围内 AC 和平台／页面有覆盖或明确缺口。共通用例保留分端操作差异，唯一用例数与平台执行范围分开统计；设计完整性与执行准备状态分别报告。

替换已有文件前校验候选文件，通过后再替换；失败保留原文件。最终回复列出实际产物路径、项目/模块/平台、关联文件、本次更新目标、数量、检查结果和未解决缺口。有实际 Git 提交时才列出 SHA。中间文件放临时目录，不混入交付目录。
