# 宿主和其他设备辅助

integration_test 控制 Flutter 应用内的组件和断言；系统界面、其他应用及跨设备步骤需要宿主或设备工具。区分实际执行能力，不因写了 WidgetTester 手势就声称覆盖了系统交互。

## 选择执行方式

| 场景 | 处理 |
| --- | --- |
| Flutter 内部文件/列表拖动 | WidgetTester 触屏或鼠标手势，验证实际业务结果 |
| Finder 文件拖入客户端 | 宿主真实拖拽或原生 UI 自动化，Flutter 等待接收及上传终态 |
| Android 权限、系统选择器、Home/恢复 | 已有 ADB/原生自动化；临时可用 scrcpy 或人工 |
| NAS 或另一客户端前置数据 | 真实 API/远端脚本；若被测功能是该端 UI，则仍需该端真实 UI |
| 注入平台 drop 回调、模拟选文件 | 只覆盖应用接收路径，明确标为模拟输入，不能代替跨应用验收 |

在本轮授权的设备和范围内，优先复用已安装的 ADB、宿主脚本或原生工具。已获授权的安装确认、运行时权限、系统弹窗与前后台切换，能力具备时直接处理。ADB 命令使用显式设备 ID，授予权限前核对应用包名和权限项，点击前核对当前弹窗及目标按钮。

执行后回读真实状态，例如确认 APK 已安装并可启动、权限已授予或目标 Activity 已恢复前台。记录失败原因并保留证据。设备系统要求本人确认、宿主命令被系统拦截或工具权限不足时，再请用户完成所需动作。

可重放的辅助动作接入测试或运行器，并在结束后恢复本轮变更的临时状态。新增框架仅在现有能力不足且收益明确时考虑。桌面真实拖拽需要可操作的前台窗口。

Computer Use 可以在工具可用且范围已授权时承担指定的宿主步骤，仍由本轮集成测试协调，不启动另一个独立执行批次。记录步骤、证据和宿主控制交还；真实系统交互不可达时记录缺口，不用模拟操作替代。

## 协作协议

Flutter 与宿主是两个独立进程，不能靠固定 sleep 猜测就绪。使用唯一 run_id/case_id 和有界握手：ready → host_action_started → host_action_done/error → Flutter assertions_done。超时记录最后阶段；宿主完成不等于业务成功。不同设备使用显式设备 ID，握手携带本轮随机标识，拒绝旧轮次消息。

例如 Finder 拖拽上传：

1. 宿主创建唯一文件，记录内容/大小/哈希；Flutter 登录并导航到独立目标目录后通知 ready。
2. 宿主把实际文件拖入目标窗口，保存操作方式和结果；Flutter 等待上传任务结束。
3. 回读 NAS 文件并校验内容，验证未误传其他文件；确认任务终态后清理本例夹具。
4. 任一步异常先留现场证据，再恢复。无法执行真实拖拽时记阻塞，不用 API 上传或合成 drop 冒充完成。

自动宿主步骤标 automation_mode=host_assisted；需要人工确认/拖拽标 manual_assisted，列出动作、设备、时间、原因和自动断言边界。报告分别展示辅助步骤与自动断言，不混为全自动通过。系统权限通常只验证授予后的业务流程；若权限流程本身是用例，需实际验证拒绝、授权等相应用例。
