# 按业务预期记录实际执行的断言

当任务需要逐项核对自动化覆盖时，从用例原文列出当前平台适用的每项业务预期。将每项预期关联到能独立验证它的一个或多个断言，映射可以保存在自动化工程或平台适配层。用例库保持只读。

## 编写断言

- 为检查点分配稳定 ID。映射至少区分模块、用例或运行入口、目标平台。预期顺序调整、插入断言都应保留原有 ID。无法确认旧代码对应哪项新预期时，显示待核对。
- 对复合预期分别验证可观察的业务结果。例如“恢复遮蔽，密码内容未变化”需要同时检查遮蔽状态和输入内容。循环内验证多个对象时，以稳定的业务角色或独立夹具标识区分必需检查。
- 每条断言写中文 reason，说明触发条件和应达到的结果。用实际控件、路由、请求、持久化或会话状态进行判断。点击、等待固定时长、打印步骤和完成清理均不能单独证明业务预期。异步检查应等待明确的结果条件。
- 按用户流程安排检查顺序。例如先验证三个字段均为空，再验证按钮禁用，最后尝试提交并检查页面与会话。保留原有失败传播和清理语义。

## 运行证据

- 在原生测试体启动时标记本次尝试。断言成功返回后上报 passed，捕获断言失败时记录 failed 并原样重新抛出。业务前置或基础设施异常按原运行器语义报告。禁止根据清单、静态代码、控制台步骤文字或整例通过推造断言事件。
- 优先复用项目已有的证据格式。每条事件至少能定位本次尝试、运行用例、断言 ID 及结果。Flutter 使用 --machine 原生 JSONL 的 testStart、testID 和终态关联。Patrol 应先在原生结果中确认对应测试，再读取同一批次、同一用例的检查事件。缺少对应的原生测试结果时，标记证据不足。
- 同一尝试中重复收到同一 ID 的事件时，保留已观察到的失败。重试、不同平台、不同用例分开统计。报告附用例和实现版本及原生证据位置。密码、令牌、验证码、真实账号和输入内容不得写入事件；需要保留的 expected/actual 只使用布尔值、数量或脱敏值。

## 报告与验收

| 证据 | 报告展示与覆盖计算 |
| --- | --- |
| 必需断言均有结果 | 该预期已覆盖。任何一条失败仍单列失败断言、业务说明和安全的期望与实际值。 |
| 某项所有已映射断言均未到达 | 单列“未执行的业务预期”，包括因前一项失败而提前退出的后续预期。 |
| 只有部分必需断言执行，或复合预期仍缺少检查 | 逐条列出已执行、未执行和缺失部分，该项未完整覆盖。 |
| 预期尚无映射 | 显示“尚未关联断言”，保留预期原文。 |
| 未启动、被跳过、缺原生证据或证据属于其他版本 | 显示相应执行状态或证据不足，不能据此自动认定覆盖。 |

所有适用预期均有完整断言证据时标记“已实现”，其余有有效证据的运行按实际缺项标记“部分实现”。业务预期、关联代码或实质性映射变化后应重新核对。历史任务仍展示运行当时冻结的解释。

验收时至少检查一次真实失败的报告。例如三个字段的空值检查通过、按钮应禁用的检查失败、后续页面与会话检查均未执行。报告应同时保留该次运行失败、具体失败断言及未执行预期，重新打开历史任务仍能逐项查看。
