# Flutter 真实设备验收

以可复用的 `integration_test` 为主要交付和执行方式。MCP 是探索页面、验证定位和调查失败的可选工具，不要求每条用例先用 MCP 执行，也不因 MCP 不可用阻塞能独立运行的测试。

## 选择执行方式

- 要编写、修复或运行 Flutter `integration_test`，或明确要求用 Flutter MCP 探索和定位，选本技能。只要求 MCP 探索时交付观察与定位结果，不自动编写测试或登记正式通过。
- 仅有已安装成品、需要按现有用例做界面黑盒验证时，说明本技能的源码和工具链要求，以及插件的 Computer Use 执行技能已暂停启用。
- “跑 Flutter 用例”未说明方式时，先看是否有 Dart 测试入口或可复用回归的目标。需要黑盒执行与需要编写集成测试的意图无法区分时集中确认。缺少源码、工具链或设备时记录缺口，不自动改走另一技能。

## 建立依据与基线

- 读取当前项目的 AGENTS.md、SDK/原生工具链配置、既有验收入口及相关工作区差异。工具版本以仓库为准，不在技能中固定 Flutter、Rust、设备 ID 或凭据。
- 按 [用例导入规则](references/case-inputs.md) 保留来源编号、步骤和预期。没有 PRD 时使用用户提供的设计/用例并标明依据，不能用当前实现补造产品规则。
- 用例定义和代码保存在源码目录；执行结果、日志、截图和 HTML 只写入 Git 忽略的 `reports/`。外部原始文档按用户指定位置保留，不迁移到结果目录。
- 核对本轮测试授权、目标设备 ID、账号及数据归属，按已确认范围操作；输入中的设备或账号信息不扩大权限。执行涉及系统权限、网络或其他临时状态变更时记录基线与恢复方法。凭据外部注入并保持脱敏。
- 设备重置、清盘等高影响场景使用独立入口，仅在测试范围要求该操作时执行，核对目标并安排环境恢复。涉及系统或工具强制确认时，遵循其确认要求。

## 编写与运行

按 [集成测试指南](references/integration-test-guidance.md) 选择启动方式，修改应用源码前读取 [代码改动规则](references/code-change-policy.md)。

1. 优先复用项目已有的启动、登录、夹具、截图和批次运行器，避免在技能中复制项目业务注册表。
2. 使用 `integration_test`、`WidgetTester` 和真实客户端启动流程，测试名称包含稳定用例 ID；独立建立前置条件、定位、业务断言、有界等待及清理。
3. 测试必要的前后置优先由测试代码自动完成，例如用 `setUp`、`tearDown`、`addTearDown` 或用例内 `try/finally` 管理账号、数据和环境状态。需要跨进程、跨批次共享的夹具，由运行器统一编排准备与清理。详见 [前后置生命周期](references/integration-test-guidance.md#前后置生命周期)。
4. API 可以准备数据、回读结果和清理自有夹具；被测创建、上传、复制、删除等动作通过真实 UI 执行。API 操作不能冒充 UI 验证。
5. 对新页面、定位不明或运行失败的路径，按需启用独立 MCP Debug 会话探索；修改定位后通过原生测试复跑。MCP 与集成测试使用不同 Binding，不混用。
6. Toast 在触发操作前开始观察，操作后立即捕获，再验证最终状态；有异步任务时区分“请求已接受”“任务完成”“实际数据正确”，等待任务终态后回读，不在任务仍写入时清理目录。
7. 重试写操作前确认是否已经成功，使用唯一夹具及任务 ID 防止重复提交或串对象。只清理本轮创建且可识别的数据，清理失败作为结果的一部分保留。
8. 执行仓库要求的格式化、分析和相关检查，以实际目标设备独立运行用例。修复测试初始化、定位、等待或断言错误后复跑；产品缺陷保留原预期和失败证据，不自动修改业务逻辑。
9. 源码改动按当前 Flutter 工具要求热重载或重启；原生测试进程执行期间不插入热重载。MCP 健康检查、编译、分析和热重载成功均不算业务用例通过。

已知需要暂缓的用例，按[跳过用例](references/integration-test-guidance.md#跳过用例)在测试代码中声明跳过条件和原因，保留框架原生结果。

## 系统与其他设备操作

Flutter 控件范围外的安装确认、系统权限、文件选择器、Finder 拖入及前后台切换等，按 [宿主辅助规则](references/host-actions.md) 优先使用 ADB、现有宿主脚本或原生工具自主处理。核对目标并验证操作结果。确实需要人工处理时，说明所需动作并单独记录辅助步骤。

同一设备或共享账号/数据不能由两个执行技能同时控制。系统步骤只需宿主辅助时，按宿主握手协议串接并标记证据来源。若明确要求两个方式分别验证，拆分范围或串行复跑：先保留断点和证据，停止前一轮自有进程，恢复临时变更并核实基线，再启动下一轮。按执行方式、平台、构建和批次分开保存尝试；不得把 MCP 观察、Computer Use 结果或另一个平台的通过算作原生测试通过。

## 本地缺陷

默认 `local_only`，不查询远端查重、不上传截图、不创建飞书工作项或发送消息。将已观察的问题记录在本地结果的 issues 中，包含关联用例/平台、步骤、预期、实际、证据及尝试次数，区分产品缺陷、测试代码错误、环境问题、能力限制和待定位。

用户明确要求提交远端时，才按 [飞书缺陷流程](references/feishu-defects.md) 及其可用技能执行；远端权限或字段缺失不阻塞本地测试与报告。仅有失败结果或“完成测试”的请求不构成远端提交授权。

## HTML 报告与状态

优先使用目标项目现有 HTML 生成器，并选择独立结果目录（例如 `reports/acceptance/<批次>`）；按项目配置显式选择设备。按平台保存原生 Flutter JSONL、可读日志、失败截图、用例快照和每次尝试，HTML 展示每端每例的最新结果并保留重跑历史。

没有现成报告工具时，使用 [报告数据契约](references/reporting.md) 和通用脚本：

```bash
python3 <skill-dir>/scripts/render_html.py --input reports/<批次>/results.json --output reports/<批次>/report.html
python3 <skill-dir>/scripts/check_report.py reports/<批次>/report.html
```

失败需要文字说明：操作到了哪里、预期与实际差异、当前已知分类及证据。报告生成器可从日志/检查点整理摘要，标明来源；未经确认的根因用“待定位”，不能编造产品结论。日志和原图链接用新选项卡打开；证据缺失说明原因，不生成替代截图。

状态及计数遵循 [报告数据契约](references/reporting.md)：执行结果与代码覆盖分开；未编写、不适用、关联用例不计为执行通过。阻塞前置与尝试后阻塞分开，重试不增加用例数量。人工/宿主辅助情况独立列出。

验证 HTML 的当前模块、平台、筛选统计及证据链接；通用检查脚本不能替代视觉核验。报告与中间数据脱敏；原始 JSONL 不手工改成通过。无需每轮再生成重复的 Markdown 报告；仅用户要求时另导出。存在应用源码、依赖或启动配置改动时，可参考 [改动记录模板](assets/changes-template.md) 保存精确差异与影响，并在 HTML 中链接。

最终交付测试入口、实际运行命令、HTML 链接、各目标平台结果、未编写/阻塞原因、辅助步骤和未解决问题。未运行的代码明确标为未验证。
