# 面向测试的需求分析

目标是把需求整理成可验证的测试输入，不替产品决定未知规则。
用户指定范围、格式和路径优先；局部更新只修改受影响内容和追溯关系。

## 分析规则

- 提取 program、module、platform，以及角色、目标、业务边界和可观察结果。
- 已确认需求、待确认推断分开。隐式需求可以列为风险或建议，未经确认不转成强制验收标准。
- 建立 REQ → AC → FP 追溯。已有编号保留；新编号记录原文位置和依据。
- FP 按独立验证目标划分，不按按钮数量拆分；一个目标可包含连续操作。
- 涉及状态、依赖、接口或跨页面流程时提取对应信息。没有依据的路径、参数、错误码、字段边界、提示文案和 SLA 不编造。
- 可说明数据分类和边界测试机会，但实际边界以已确认业务规则为准。
- 局部缺口不阻断其他已确定内容。只有无法识别需求对象或主要目标时才需先补充输入。

## 产物

使用 `references/requirements_template.md`。核心章节保留；按需章节不适用时标记 N/A 并简述原因，不凑表格。

输出根目录依次使用用户指定目录、输入所在测试根目录、工作区 `4-test_cases`、回退 `test_cases`。默认保存 `{根目录}/{项目}/{模块}/需求分析_${TIMESTAMP}.md`，时间取当前当地时间。更新保留 created、更新 updated。

## 完成条件

- 显式需求能定位来源，已确认 AC 可观察，FP 关联 REQ 和 AC。
- 推断和未知规则未被包装为确认事实。
- 缺口含影响、关联编号、待确认问题及 P0/P1/P2：按业务影响定级，严重安全/数据风险可为 P0。
- 自检后修复遗漏；缺少外部信息的项保留为缺口，不能自称已消除。

交付文档链接、关键缺口及自检摘要，不默认生成计划和用例。
