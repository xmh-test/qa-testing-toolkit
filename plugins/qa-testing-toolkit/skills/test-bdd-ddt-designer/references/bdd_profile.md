# BDD 完整业务旅程设计规范

## 先构建业务旅程

不得看到一个功能点或一条常规用例就立即生成 Scenario。先通读同一模块的需求和已有用例，形成内部业务旅程图。

每条候选旅程至少识别：主要角色及权限、业务目标与对象、初始状态、触发条件、必要动作、关键状态转换、可观察检查点、最终结果、异常分支、清理责任，以及关联的 REQ、AC、FP 和常规用例。

旅程图是设计过程，不强制创建独立文件。快速设计模式应在交付总结中展示；资产增强模式可直接用于 Feature 与覆盖关系。

## 场景粒度

- 一个 Scenario 对应一个可独立验收的业务结果闭环，原则上只有一个主要角色、一个主要业务目标、一个明确初始状态和一个最终业务结果。
- 场景通常包含入口、关键动作、状态变化、必要检查点和最终结果。
- 不规定机械的最少 When 数量；只有当单一动作本身即可完成业务目标时，才允许只有一个 When。
- 不要把“点击按钮”“打开菜单”“输入一个字段”单独作为 BDD 场景，除非该动作本身就是被验收的业务行为。
- 步骤数量不是场景边界；同一目标内的连续操作保留为完整流程。
- 一个 Scenario 可以覆盖多个 FP、AC 和常规原子用例。覆盖多不等于范围过大。

## 合并规则

同时满足下列大部分条件时，优先合并为一条完整 Scenario：

- 相同主要角色和权限上下文；
- 操作同一业务对象；
- 服务于同一个主要业务目标；
- 属于连续且不可割裂的状态生命周期；
- 中间动作单独成功没有独立业务价值；
- 多个断言共同证明同一个最终结果；
- 测试数据创建、使用和清理属于同一个闭环。

## 拆分规则

满足任一条件时通常应拆分：

- 包含两个可分别验收的业务目标或最终结果；
- 操作不同业务对象，且失败和清理可以独立处理；
- 前半段完成后即使后半段失败，前半段仍是一项有价值的独立成果；
- 执行路径或状态转换实质不同；
- 角色、权限或平台业务预期不同；
- 包含不可逆或破坏性状态变化，需要独立隔离；
- 测试数据和清理责任互不相干；
- 标题必须依赖“并且还要”“随后再完成另一件事”才能描述清楚。

不要为了减少用例数量而把多个互不相关的结果串成长流程。

## 共享前置条件与 Background

前置条件相同不代表场景应合并。多个独立业务目标共享登录、设备在线或已有基础数据时：

- 所有 Scenario 真正共享且不会隐藏关键业务规则的静态上下文可放入 `Background`。
- 与特定结果直接相关的状态仍写在该 Scenario 的 Given 中。
- Background 只是描述复用，不表示运行时共享前一场景留下的状态。
- 每个 Scenario 必须自行建立可重复的前置状态。

## 独立性与清理

每个 Scenario 必须可单独选择、重复执行，不依赖另一场景的顺序或成功；使用唯一或可重置的数据，清理自己创建或修改的数据，并确保失败后不污染后续场景。

自动化 Fixture 可以复用高成本公共前置，但 Feature 仍需表达业务前置，Fixture 不能制造跨场景状态依赖。

## 反碎片化审查

生成 Feature 前逐条复核：

1. Scenario 数量是否只是照搬功能点或原子用例数量；若是，重新聚合旅程。
2. 标题是否只描述页面、按钮、字段或单个操作；若是，向上寻找其服务的业务结果。
3. 删除某个中间步骤后是否仍能完成同一目标；若不能，该步骤属于旅程，不应单独拆出。
4. 场景是否包含两个可分别执行和验收的结果；若是，拆分。
5. 是否因前置相同而合并不相关目标；若是，改用 Background/Given。

通常一个完整业务场景会包含 2～8 个关键业务动作，但这只是人工审查信号，不是硬性数量限制。

## 场景标题

- BDD 标题不套用常规原子用例的方括号四段式，使用可独立阅读的自然中文；建议 15～50 个汉字，以完整表达业务意图为准，不作为机械长度校验。
- 普通 Scenario 标题表达“角色 + 完整业务动作链 + 最终业务结果”，例如：`管理员发现已初始化设备并登录系统桌面`。
- Scenario Outline 以及 BDD+DDT 标题表达“角色 + 使用/提交参数化数据 + 业务目标”，例如：`管理员使用不同凭据完成登录认证`。各数据行的成功、拒绝和错误提示写入 Examples/DDT rows，不在标题逐项枚举。
- 负向普通 Scenario 可以在标题写明最终拒绝结果，但仍需体现业务动作，例如：`未授权用户访问管理入口时被拒绝并保留当前页面`。
- 标题不得包含 `BDD`、case/scenario/dataset ID、`<参数占位符>`、按钮级操作，或“测试/验证/检查某功能”等设计方法措辞。
- 与场景关联的 JSON 模板 `title` 必须与 Feature 中 Scenario/Scenario Outline 标题逐字一致。

## Gherkin 格式

- 使用英文 `Feature`、`Background`、`Scenario`、`Scenario Outline`、`Given`、`When`、`Then`、`And`、`Examples`。
- 标题、步骤和说明使用中文。
- Given 描述角色、前置状态和必要数据；When 描述完成目标的动作链；Then/And 描述可观察的中间检查点与最终结果。
- Then 不断言内部实现细节；页面、状态、提示、数据变化或可查询结果必须可观察。
- UI 导航只保留理解业务流程必需的部分，不写自动化定位器或实现细节。

## 标签与追溯

资产增强模式的每个场景至少包含：

```gherkin
@BDD-FP001-001 @TC-FP001-010 @FP-001 @REQ-001 @AC-001 @P0
@covers-full-TC-FP001-001
@covers-partial-TC-FP001-002
Scenario: 管理员完成登录并进入设备主页
```

- `@BDD-*` 与 JSON `bdd_scenario_id` 一致。
- `@TC-*` 仅指向同步写入常规 JSON 的这一条完整流程/模板用例。
- `@covers-full-*`、`@covers-partial-*` 只指向已有常规原子用例。
- 需求、验收标准、功能点或覆盖 ID 有多个时逐项加标签。

以上完整标签要求仅适用于资产增强模式。快速设计模式没有既有 ID 时，只使用需求中真实存在的标签和优先级，不得编造 `@TC-*` 或覆盖标签。

Feature 顶部可用注释记录来源：

```gherkin
# source_cases: 测试用例_20260806_100000.json
# generated_at: 2026-08-06 10:10:00
```

## 普通 Scenario 与 JSON

- 一个 Scenario 同步一条 JSON 完整流程用例。
- JSON `steps`/`expected` 展示完整流程，不能只保留最后一个动作。
- 除标题必须逐字一致外，Feature 与 JSON 的步骤可以因表达形式不同而不逐字一致，但角色、前置、关键动作、检查点和最终结果必须一致。

## Scenario Outline 与 DDT

- 只有角色、前置、动作路径、状态转换和断言结构相同，仅输入与对应预期变化时，才使用 `Scenario Outline`。
- 客户端格式拦截、服务端认证拒绝、网络异常或权限拒绝等不同执行路径，默认拆成不同 Outline/dataset。
- Outline 只同步一条 JSON 参数化流程用例，不按 Examples row 展开。
- Examples 必须包含 `row_id`，每行与 DDT JSON 对应 dataset 的同名 row 一致。
- 参数列、具体值和结果字段必须能与 DDT `parameters`、`values`、`expected` 一一对应。
- BDD+DDT 覆盖标签与 dataset `coverage` 完全一致。

## 去重

- 同一行为不得同时生成普通 Scenario 和 Scenario Outline。
- 多个平台仅在交互路径、业务规则或预期实质不同时拆场景；只有布局和定位方式不同，由自动化适配层处理，不复制业务 Scenario。
- `Background` 只放所有场景真正共享且不会隐藏关键业务条件的上下文。
