# 飞书缺陷整理与提交

适用于不同模块，不内置特定项目、平台、设备或人员配置。

使用 Meegle 飞书项目 CLI 工具（[项目地址](https://github.com/larksuite/meegle-cli)），安装与认证问题单独处理。

## 内容原则

让他人看得懂，并能在自己的环境复现。只写用户提供、实际观察或可信测试记录支持的事实，不补造条件、预期规则、原因或复现频率；未验证问题不能写成已确认缺陷。

- 保留必要的本地操作及与客户端的交互，不限定步骤发生在客户端内。
- 将个人文件名、路径、设备地址等偶然信息泛化，保留影响复现的类型、大小、数量、权限及特殊名称／路径特征。例如“从本地电脑拖拽一个 MP4 视频文件到客户端上传”。
- 正文写可执行的操作和可观察的结果，不叙述 Figma／原型依据或测试者内部工作过程；必要的数据准备写成通用步骤，排查细节放备注。凭证不写入缺陷。
- 信息缺失、歧义、冲突，或不确定某条件是否影响复现时，先集中询问用户，不擅自补写、删除或泛化；确认前不提交受影响条目。跟踪平台不等于实际复现平台。

## 六项结构

| 字段 | 内容 |
| --- | --- |
| Bug 标题 | `[功能模块] 触发条件与具体故障现象`，避免“功能异常”等空泛表述 |
| 前置条件 | 必需的环境、状态、权限和测试数据条件 |
| 操作步骤 | 按顺序描述操作，页面和按钮使用实际名称 |
| 预期结果 | 应出现的行为或结果，可包含本地文件结果 |
| 实际结果 | 观察到的现象、提示原文或文件结果，附与问题匹配的真实证据 |
| 备注 | 必要日志、接口报错、复现频率等排查信息；无内容可留空 |

## 证据与呈现

- 必须有能支持该条实际结果的真实证据。界面问题优先使用截图；接口、后台任务、性能等问题可使用请求响应、日志、测量记录或视频，不把截图作为所有缺陷的提交前提。
- 截图可来自客户端、本地目录或其他相关现场，必要时多图对比并说明各图现象。不制作模拟界面或伪证据；标注不改变事实，画面完整、清晰可读。
- 证据优先通过富文本呈现：支持内嵌的截图、GIF／视频放在“实际结果”相关文字之后；简短的请求响应、日志或测量记录用文本、代码块或表格呈现，排查细节放备注。按当前 Meegle 工具的富文本及图片上传规范使用真实返回的引用，不手工拼接上传地址或资源标识。
- 富文本不支持该格式、超过当前工具／平台限制，或内容过大影响阅读（如大量日志）时，改用附件；正文保留证据摘要、文件名及对应现象，必要时摘录关键片段。不能因改用附件而省略关键证据，也不把上传成功等同于正文可见。
- 缺少截图但已有足够的其他证据时可继续提交；证据不足时，在授权范围内补齐，无法取得则说明并集中询问用户，不提交受影响条目。不为补证据扩大设备、数据或操作权限。

## 执行与校验

1. 检查登录状态，读取当前项目与字段定义；按需查询选项、关联项和人员，用真实元数据解析 ID，不猜测或硬编码。
2. 新建时去重并确认问题依据；按当前模板一次性收集缺失的批次配置（如优先级、严重程度、模块、环境、版本、关联项、人员和其他必填字段），可选项可留空，列明单条例外。沿用用户明确且仍适用的规则，不把历史条目自动当默认值。向用户展示名称。
3. 优化已有缺陷时先读原文、证据及可用的版本标识，只更新本次授权的内容，保留其他字段；无需重新收集整套新建配置。每次写入前（包括修正和重试）重新读取待更新字段，与初读版本比较；若有他人或自动化新增内容，基于最新版本合并并保留非本次修改的内容与证据，无法无歧义合并时停止该项并询问用户。有版本号／条件更新接口时使用其防止覆盖；版本冲突后重新读取，不用旧内容强行重试。
4. 写入前展示整理结果与证据情况；已有明确授权且信息齐全时执行，不重复确认。缺失信息按内容原则先询问。
5. 批量串行写入；每条回读标题、描述、目标字段及证据，按上述证据呈现规则检查富文本显示及附件关联，必要时打开页面确认可见。字段被自动化覆盖或证据异常时修正并回读；无法修复则报告并询问，不标记完成。
6. 部分失败时保留成功项，仅重试失败项；创建结果不明时先查询，避免重复。修正后仍不一致或重复失败时停止该项。空成功响应不代表完成。
7. 最终列出标题、ID／链接、校验结果及未解决事项。
