# QA Testing Toolkit

面向中文软件测试工作流的 Codex/ChatGPT 插件集合，提供需求分析、测试资产导出、Computer Use 测试执行及已确认问题的缺陷整理与提交能力。

## 包含的 skills

| Skill | 用途 |
| --- | --- |
| `test-requirements-analyst` | 分析 PRD 和需求，输出可追溯的测试设计输入与需求缺口 |
| `test-ui-designer` | 仅有 Figma/HTML 设计稿时，提取测试功能和证据，衔接常规用例生成 |
| `test-plan` | 生成或更新结构化测试计划 |
| `test-case-generator` | 通用用例设计，按上下文引用场景扩展，生成或更新 JSON V3 及总结 |
| `test-case-reviewer` | 评审用例结构、覆盖、可执行性及业务规则依据 |
| `test-case-to-sheets` | 将测试用例 JSON 转换为本地 Excel 文件 |
| `test-executor`（Beta） | Computer Use 多平台测试执行，明确范围、保存证据、统计结果并恢复环境 |
| `test-bug-submit` | 查重后提交飞书项目缺陷，同一问题补充已有 Bug，已解决或已关闭且再次复现时重开，写后回读校验 |

## 安装

添加公开 marketplace：

```bash
codex plugin marketplace add xmh-test/qa-testing-toolkit
```

安装并启用插件：

```bash
codex plugin add qa-testing-toolkit@qa-testing-toolkit
```

安装后请新建一个 Codex 任务，让新任务加载插件中的 skills。

建议只保留一种技能来源；若工作区还有同名独立技能，应同步更新或移除旧副本，避免加载不同规范。

## 0.8.1：技能指令精简与 Bug 字段口径

**使用提示：`test-executor`（执行用例技能）暂不要使用，等待后续验证通知；其他技能正常使用。**

`test-bug-submit` 新建时按默认定义分别判断严重程度与优先级，并映射项目真实选项。影响范围必填；复现频率仅按输入提供的信息填写；运行平台由输入确认，暂不收集部署环境。本次被测版本必须提供，其他版本仅按可信信息记录。模块、分类及关联项唯一匹配时自动填写，有歧义或缺必填项时集中确认。纯体验诉求列为优化建议，缺陷预期依据不清时先确认。补充或重开已有 Bug 默认保留原等级，新证据表明影响变化时提出等级与理由，确认后调整。

清理技能中的会话复盘和项目历史记录；开发验证说明移至仓库文档，执行范围、恢复和设计方法按引用集中维护。测试计划按风险和协作需要组织内容，模板独立提供，不设置行数或功能项数量建议。

## 0.8.0：测试执行 test-executor（Beta）

**当前状态：Beta。** 测试执行技能已合并主线，仍处于试用验证阶段；脚本自动测试通过不代表真实设备端到端无人值守能力已全面验证。已验证范围及现场验证限制见[开发与验证说明](docs/test-executor-development.md)。Beta 标记仅适用于 `test-executor`。

新增[无人值守测试执行技能](plugins/qa-testing-toolkit/skills/test-executor/SKILL.md)，先确认用例范围与资源，再验证环境和授权，使用 Computer Use 执行已有用例、记录证据、去重缺陷并输出执行记录、Excel及测试总结。默认纳入全部常规功能用例，专项按明确范围启用；冒烟、功能、回归、兼容性及指定清单的[范围规则](plugins/qa-testing-toolkit/skills/test-executor/references/scope.md)分别定义，不以优先级代替冒烟集合。

本机平台优先，发现问题后复核其他目标平台；每端结果独立记录。产品问题/功能缺失导致无法继续计为阻塞，环境或授权不足计为未执行。SSH默认只读。暂停、切换任务、交还设备及结束时都恢复本轮代理等环境变更；停止辅助工具后，必须实际验证客户端正常使用。缺陷默认本地记录，外部提交和消息发送按用户授权处理。

技能提供参数化HTTP故障代理和移动端、多语言、浏览器兼容性参考。代理不支持HTTPS解密或精确截断已有HTTPS下载流；工具命中与业务结果均需实际证据。执行记录协议独立于设计用例V3，不改变现有生成、评审和设计用例导出格式。

调用示例：“使用 $test-executor 执行这份用例的冒烟测试，在 macOS 和 Android 上验证，暂停或结束前恢复环境并验证客户端可用。”

## 0.7.0：Bug 提交、查重与重开

将 `test-defect-filing` 更名为 `test-bug-submit`，展示名称为“bug提交”。新名称用于显式调用；原名称不再保留为独立入口。该技能将已确认的问题整理为包含标题、前置条件、操作步骤、预期结果、实际结果和备注的缺陷，支持批次配置、项目与批内查重、已有 Bug 补充与重开、串行提交和写后回读校验；不负责问题验证。

同一问题优先复用已有 Bug：活跃状态补充新增信息，已解决或已关闭且本次确认仍存在／再次出现时按项目流程重开；疑似重复先确认。创建结果不明先回查，不能因一次查询为空就自动重建。新建或重开默认指派给当前飞书项目工具授权用户，明确指定时优先遵守；仅追加评论保留原经办人。新建描述及每次补充均注明本次被测程序的平台、名称和版本，重开说明与补充证据优先写评论，保留原描述。

证据优先以富文本呈现，不支持或内容过大时使用附件；日志、响应、测量记录或视频可作为适用证据，不强制所有问题提供截图。更新已有缺陷时，每次写入前重新读取并保留同期修改，冲突时停止该项。

使用 Meegle 飞书项目 CLI 工具（[项目地址](https://github.com/larksuite/meegle-cli)），安装与认证问题单独处理。

调用示例：“使用 $test-bug-submit，将这些已确认的问题提交到指定飞书项目，证据优先放正文，大量日志使用附件。”

## 0.5.0：通用设计与按需场景扩展

`test-case-generator` 仍是统一入口，标题、粒度、追溯、确认与V3协议不变。先区分产品、运行平台、架构和能力，读取[扩展入口](plugins/qa-testing-toolkit/skills/test-case-generator/references/extensions/index.md)，再仅读取适用文档；不是为每个产品另建skill，也不一次加载所有专项。

| 扩展维度 | 当前提供 |
|---|---|
| 产品 | NAS设备、数据及网络/服务路径 |
| 平台 | 移动端（后台、熄屏、回收、网络及触控）、Web、独立桌面客户端 |
| 架构 | C/S与设备/云协作、受理/回执/任务及数据归属 |
| 能力 | 身份/多用户/并发；部署/依赖/版本 |

这些可组合使用，未知能力先确认。例如NAS手机端可结合NAS、移动和已知的C/S，再按账号与部署能力选择相应扩展；离线单用户Web工具只用实际适用项。扩展是风险设计参考，不是产品需求、固定阈值或执行授权。项目规则留在项目依据，不写入公开通用文档。

逐功能检查操作时序、已有/残留资源、具体故障路径、身份变化和恢复后续操作，避免只按页面生成或用一条笼统失败代替多种机制。记录扩展风险到FP/用例/候选的处置；需求内未知策略、范围未知和环境待准备分别处理，不误判需求外。生成、UI提取、评审共用相同扩展，重叠场景复用而不膨胀数量。

新增扩展只需在references/extensions新增有边界的文档并登记读取条件，不改主数据协议。Figma不默认下载截图的规则继续有效。

## 0.4.2：Figma截图按需留存

默认在线读取视觉信息，不主动将Figma截图下载到本地或交付目录；追溯保留节点链接、读取时间、范围清单及必要分析结论，不以原始结构快照代替截图留存。需要留存时先确认用途、节点范围与保存位置，再保存最小必要内容。工具若只能下载后看图，同样先确认；工具自行管理的缓存不在此承诺范围。未保存截图不是覆盖缺陷，未完成视觉读取则仍应如实标明。

## 0.4.1：设计范围防遗漏

分析设计稿前先盘点全部可访问平台、页面及相关分区/状态稿，记录纳入、排除、待确认及读取状态；不能将链接起始节点或已有PC用例默认视为完整范围。支持同页多平台及HTML响应式布局识别，用户明确的局部范围仍优先。目录权限不足时明确全貌未核验，不伪称只有当前平台。

生成和评审均从总览逐项反查FP及用例/候选或具体不适用说明。共通规则复用不等于交互照搬：各端入口、布局、返回、载体及生命周期分别核对，要求分别执行。唯一用例数和各平台执行范围分开统计；遗漏纳入平台或核心页面不得通过覆盖自检。沿用V3与现有Excel格式，不增加业务字段。

## 0.4.0：风险展开与规则确认

逐功能点审视用户操作异常、系统/外部异常、恢复和数据保护；核心状态变更设计从发起到实际对象、业务或数据结果的核验。按已知能力选择网络路径、对象/设备/作用域切换及依赖版本等代表风险，不以条数或分类数判定覆盖。

已有功能的通用质量目标可设计异常用例，未知专有策略以候选方案分批确认。使用弹窗时一次提交多个独立问题，每批最多10题；共性决策合并、实际答复与版本范围保存到项目记录，随后同步用例。V3协议、六个test-技能名称及Excel导出保持一致。

## 技能命名

全部技能名称和目录统一以 `test-` 开头。需求分析使用 `test-requirements-analyst`，UI 设计分析使用 `test-ui-designer`。显式调用请使用新名称；其余技能名称和功能保持不变。

## UI 功能测试设计

使用示例：“没有 PRD，请根据这些 Figma 页面（或 HTML 原型）提取测试功能，编写测试用例并导出 Excel。”

新技能按六个维度提取：页面入口、用户目标、操作反馈、数据约束、状态分支、对象影响。按独立目标聚合功能，不将控件机械转成用例。规则标注已明确、部分明确或待确认，并保留节点/文件证据。

根据明确功能意图设计操作、反馈及结果链路。已有功能的失败不误报、对象不串用、资源不误伤等通用质量目标可以形成异常用例；未知专有策略单列候选并确认。区分规则缺口与执行准备缺口：确定用例进入 JSON，环境尚未就绪时记录具体准备事项。未确认候选不混入 JSON 或 Excel，不计入确定覆盖；数据协议仍为 V3。

默认交付 UI 测试依据；要求用例时继续生成 V3 JSON 与总结，Excel 按需导出。仅提取请求不自动生成全部产物，既有 PRD 流程不变。

本技能负责测试设计，不执行程序或判断界面还原度。HTML 实现不能作为验证自身正确性的唯一基准。Figma 读取依赖可用连接器和权限；访问不足时说明可读范围。

## 数据与工作流

八个技能按用户任务选用，不强制跑完整链路。用例设计默认生成 JSON 明细和 Markdown 总结，内部自检不额外输出评审报告；Excel 按需导出。缺陷提交独立使用，不自动执行测试、验证问题或转换用例数据。

新数据使用 V3：13 个用例字段，Excel 为序号加 13 列。标题使用 `【功能分类】【场景摘要】核心操作，预期结果`，一条用例围绕一个独立验证目标。

设计资产生成与导出不提供旧版专项场景/数据集设计、关联字段、覆盖过滤及专项 Excel 列；执行技能可按明确范围执行用户提供的专项用例，执行统计与范围筛选使用独立协议。保留旧版纯常规 V1/V2 的只读导出兼容；旧版混合资产明确报错、不静默删减。旧文件升级默认另存 V3，不覆盖历史资产。旧版输入只保留最小兼容识别逻辑。

生成器、评审器、导出器共享数据校验；结构通过不代表业务覆盖完整。技能应整体安装，不能单独复制依赖共享脚本的导出器。
